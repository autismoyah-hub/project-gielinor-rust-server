# Contributing

Choose a GitHub issue, retain its GR identifier, and discuss the intended scope. Check the exact current source before treating older research as authoritative. Link Wiki revision evidence and distinguish gameplay requirements, project policy and revision-specific identifiers. A 184 identifier or contemporary Wiki value is not automatically correct for 239.1.

Make focused Rust changes in the authoritative development process. Add deterministic synthetic tests, then document action timing, server outcomes, native display and same-save relogin where the issue requires them. Include exact source/build/cache identities in acceptance evidence without uploading the cache. Record expected/actual behavior and unsupported cases. Run BUILDING.md commands.

Document the source and license of every contribution. Original Rust contributions use the project's ISC declaration; preserve third-party attribution. Do not submit proprietary cache/gamepack assets, original decompiled Jagex Java, private fixtures, credentials, databases or copied Kronos implementation without established permission. A behavior reference or source citation is not source-reuse permission. Do not paste unreviewed copyrighted source into Issues.

Submit a pull request for owner review. Community changes must be reconciled into the authoritative Agent 2 source before the next source checkpoint; release synchronization must never overwrite accepted PR work with an older local snapshot. The owner controls acceptance and merge. No auto-merge or automatic issue closure is authorized.
