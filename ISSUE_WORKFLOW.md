# Wiki issue workflow

Backlog: https://github.com/autismoyah-hub/project-gielinor-rust-server/issues. At inspection there were 24 open issues and no closed issues, with four comments. Counts are a timestamped observation, not a fixed project total. Agent 4 continues publishing/refining requirements; existing IDs and comments were not altered.

Bodies carry stable GR identifiers and intended categories such as `wiki:validation`. Actual label arrays were empty in the inspected issues: do not present those intended categories as applied GitHub labels. Agent 4 explicitly deferred labels until supported discovery becomes available. No configuration changes are needed to preserve the backlog when visibility changes.

Issue sections include Wiki revision links, current Rust coverage, local Kotlin versus original Project Gielinor distinctions, Kronos behavior comparisons, proposed Rust/test pseudocode, acceptance criteria and dependencies. Pseudocode is design guidance, not a claim of compilable current APIs. Kronos references retain LEGAL_PROVENANCE_HOLD for direct source reuse.

IMPLEMENTATION REQUIRED means an inspected missing path; PARTIAL IMPLEMENTATION identifies bounded gaps; IMPLEMENTED — VALIDATION REQUIRED means source exists without full runtime evidence; KOTLIN PORT PENDING requires an established port gap. UNKNOWN is not absence. VERIFIED COMPLETE requires every applicable mandatory criterion on identified source, fixture, runtime and persistence state.

Lifecycle: select/scope issue → verify identifiers and dependencies → Agent 2 or contributor implements in the authoritative development process → deterministic tests → required native/server/save acceptance → owner review → owner-approved merge/checkpoint → issue closure only with complete evidence. Agent 3 packages/pushes reviewed snapshots; it does not redefine gameplay behavior or close issues automatically.
